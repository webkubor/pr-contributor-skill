> 用途：阶段 6 · 开 PR 时按上游约定准备标题与五块正文，让维护者在第一屏判断价值与风险。

# 标题与正文的写法

先确认阶段 3 · 价值门禁已通过，阶段 5 · 写改动已有项目自身命令的验证证据。
优先采用上游标题约定；下表用于上游采用 Conventional Commits 的情况。
正文固定使用主入口的五个二级标题，顺序不变；无截图时也保留该块并说明原因。

## 标题选 type、scope 与行为

| type | 适用场景 | 反例 |
|---|---|---|
| fix | 修复已确认错误行为 | `fix: rename local variables` 没有 bug |
| feat | 上游接受的新能力 | 未获支持就新增产品方向 |
| docs | 修正误导操作的文档 | 把实现变更藏在 docs 下 |
| test | 补有外部理由的回归覆盖 | 用测试 type 掩盖生产逻辑变化 |
| perf | 有真实场景与测量的性能改善 | 没测就写“更快” |
| refactor | 上游认可、范围明确的结构调整 | 以重构偏好起手，四道门未过 |
| chore | 上游接受的日常维护 | 没 issue 依据的依赖升级 |
| build | 构建相关的有效问题 | 借此改禁止的 lock 或生成物 |
| ci | 标题约定可能允许此 type | 本 skill 不因此获得改 CI 权限 |
| style | 上游可能接受的格式类 type | 本 skill 拒绝纯格式化 PR |
| revert | 撤销已确认的回归提交 | 没说明回退影响就撤整块功能 |

类型存在不代表该类候选可提交；仍受四道门与硬红线约束。
scope 从上游已有模块名、包名或用户入口取，不自造全仓从未出现的缩写。
若上游限制 scope，用其枚举；scope 可选时，只有能缩小影响范围才添加。
建议标题总长不超过 72 字符，上游限制更严格则服从上游；不是机械截断句子。

| 弱标题 | 可判断的标题 | 改进点 |
|---|---|---|
| `fix: update parseValue` | `fix(parser): return empty result for blank input` | 描述用户输入与结果 |
| `docs: update README` | `docs: correct the command for running parser tests` | 说明命令用途 |
| `fix: various issues` | `fix(config): preserve explicit zero timeout` | 一个 PR 一件事 |

当函数名无法解释用户症状时，写用户可见行为；只有内部契约本身是问题时才突出函数名。
公共 API 签名或默认行为改变必须在标题/正文显露；先按 guardrails 的边界确认方向。
不要把未测的效果写进标题，例如“eliminate all crashes”或“double performance”。

## 五块正文怎么写

| 标题 | 写什么 | 建议长度 | 可判定要求 |
|---|---|---|---|
| 什么变了 | 行为变化与必要实现 | 1～3 句 | 能对上 diff，不只说改了文件 |
| 为什么 | 用户症状、根因、issue | 2～4 句 | 有外部理由，解释为何需要 |
| 怎么验证 | 环境、命令、步骤、前后结果 | 3～8 行起 | 维护者可复制，区分已跑/未跑 |
| 影响面 | 模块、兼容性、边界、风险 | 1～3 句 | API/默认行为有无改变都写事实 |
| 截图 / 日志 | 对比图或最小脱敏日志 | 0～2 图或短日志 | 无附件写不适用及原因 |

“什么变了”回答怎么改，但先写行为，再写必要的实现；不要堆函数清单。
“为什么”回答不改会怎样；issue 号不能替代症状说明。
“影响面”不能复制模板里“不改 API”后不核实；依实际 diff 改写。
五块不是五份重复摘要；同一个验证事实只在“怎么验证”展开。

## 验证块的可复制格式

命令必须来自项目 workflow/package scripts，下面仅演示一个假设有 parser 测试脚本的项目。
使用前替换为目标项目真实命令，不能声称示例命令已在目标项目通过。

````markdown
## 怎么验证
环境：Node <VERSION>，<PACKAGE_MANAGER> <VERSION>，HEAD <SHA>。
已执行：
```bash
npm ci
npm test -- parser
npm run lint
```
复现：
1. 在 <入口> 输入 <最小合成输入>。
2. 修复前：<精确错误或输出>。
3. 修复后：<精确输出>；正常输入 <样例> 保持 <结果>。
回归证据：新增 <测试名> 在修复前失败、修复后通过。
未执行：<检查名>，原因 <具体限制>；不能据此宣称全量验证通过。
````

命令前说明工作目录；依赖版本、时区或 locale 会影响结果时写明。
勾选框只勾已实际执行的检查；失败、跳过、未执行分开记录，不把 exit 0 当全部 CI 通过。
日志只保留第一处错误与相关断言；去掉路径中的个人信息、token、内部地址与真实输入。

## 正面例子一：局部 bug 修复

标题：`fix(parser): return empty result for blank input`
以下是写法示范，测试名与命令应来自真实项目证据。

```markdown
## 什么变了
空字符串现在返回空结果；解析前先处理空输入，正常文本仍走原解析路径。

## 为什么
Fixes #123
当前空输入会进入首元素读取并抛异常，调用方无法把“无内容”作为正常结果处理。
issue 中给出的空字符串可稳定复现。

## 怎么验证
Node 20，npm 10；在仓库根目录执行 `npm test -- parser` 与 `npm run lint`，均通过。
新增 `blank input returns empty result`：只加测试时失败，应用实现后通过。
复现：传入空字符串 → 修复前抛异常 → 修复后得到空结果。
普通文本与多段文本测试保持通过；全量构建未执行，原因是本地缺少构建服务。

## 影响面
仅影响 parser 的空字符串路径；公共 API 签名不变，正常输入行为不变。

## 截图 / 日志
无 UI 改动，截图不适用。断言摘要：空字符串的实际结果与预期空结果一致。
```

可取处：首句给行为，issue 提供理由，验证明确先失败后通过，也披露未执行项。

## 正面例子二：文档命令修复

标题：`docs: correct the command for running parser tests`

```markdown
## 什么变了
README 的 parser 测试命令改为项目当前提供的 `npm test -- parser`。

## 为什么
Refs #124
文档仍引用已不存在的 `test:parser` 脚本，按入门步骤执行会得到 missing script。
当前 package scripts 与 PR workflow 都通过 `test` 接收筛选参数。

## 怎么验证
在干净检出中按 README 的安装步骤执行 `npm ci`，再执行 `npm test -- parser`，通过。
修复前执行文档旧命令得到 missing script；修复后能运行 parser 测试。
验证环境为 Node 20、npm 10；同时检查正文中的命令与 package scripts 一致。

## 影响面
只更新测试说明，不修改运行时代码、公共 API 或依赖版本声明。
issue 还包含其他文档问题，所以仅引用，不关闭整个 issue。

## 截图 / 日志
无 UI 改动。日志摘要：parser 测试通过，未包含机器路径或用户输入。
```

可取处：文档修复也实际执行命令；没有用 Closes 误关尚未完成的 issue。

## 反面例子一：没有信息的正文

```markdown
## 什么变了
修复了 bug。如题。
## 为什么
fix(parser): update parser
## 怎么验证
应该可以了。
## 影响面
无。
## 截图 / 日志
见全部日志。
```

问题：复制 commit message 当原因；无症状、无命令、无前后结果，“无影响”不可核实。
改造：按正面例子一填实际输入、错误、回归测试与模块边界；没有证据就回阶段 5。

## 反面例子二：把范围藏进日志

```markdown
## 什么变了
一些小清理。
## 为什么
Closes issue 125，也顺便升级所有依赖、重写配置入口。
## 怎么验证
粘贴了几千行安装日志，没有写退出码或测试命令。
## 影响面
没有写。
## 截图 / 日志
完整终端截图，包含个人路径与未脱敏数据。
```

问题：关闭语法缺 `#`；混入无关修复，范围不可判断；长日志不能替代验证，也有泄漏风险。
改造：去掉无关改动，按四道门重筛；只贴必要脱敏证据，按事实写 API 与依赖影响。

## issue 关联语法

| 写法 | 效果 | 何时用 |
|---|---|---|
| `Fixes #123` | 满足关闭条件时自动关闭 | 完整修复一个 bug |
| `Closes #123` | 满足关闭条件时自动关闭 | 完整解决一个 issue |
| `Fixes OWNER/REPO#123` | 跨仓关闭引用 | 确认目标仓与权限语义 |
| `Refs #123` | 普通引用，不自动关闭 | 部分解决、相关背景 |
| `见 issue #123` | 文字引用，不自动关闭 | 说明关联但不承诺完成 |

关闭关键词通常在 PR 合入目标仓默认分支时生效；提到其他 base 时核对平台规则。
`Fixes` 与 `Closes` 的自动关闭效果相同；`Refs` 不是关闭关键词。
多个 issue 分别写 `Fixes #123`、`Fixes #124`，避免用不清楚的列表表达关闭关系。
不要在模板未替换时发布 `<ISSUE_NUMBER>`；没有 issue 就写清用户症状，不伪造编号。

## 维护者的 30 秒判断标准

第一屏依次回答：哪个行为变了、谁会遇到、为什么值得改、改动边界在哪里。
接着给出能复制的验证入口，让维护者不用翻完整 diff 就知道证据在哪里。
标题加第一段仍无法说出合入收益，就重写；正文超过需要时先删过程叙述与重复日志。
开 PR 前使用主入口的 `scripts/pr-lint.mjs`，机械检查不能替代事实核实。
