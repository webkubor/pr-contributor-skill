> 用途：阶段 7 · 跟进到终局时诊断 CI、逐条处理 review，并按明确终态结束贡献。

# CI 排障与 review 应对手册

先确认失败对应自己的最新 PR 和提交；禁止靠连续重跑掩盖确定性失败。
下面在目标仓目录执行；先替换仓库、PR 号与 run ID，不处理别人的 PR。

```bash
REPO=OWNER/REPO
PR=123
gh pr view "$PR" -R "$REPO" --json url,headRefOid,headRefName,baseRefName,state
gh pr checks "$PR" -R "$REPO"
SHA=$(gh pr view "$PR" -R "$REPO" --json headRefOid --jq '.headRefOid')
gh run list -R "$REPO" --commit "$SHA" --limit 30 \
  --json databaseId,headSha,event,workflowName,conclusion,url
```

`gh pr checks` 返回非零可能是失败或待完成；pending 的专用退出码为 8。
用 `gh pr checks "$PR" -R "$REPO" --required` 看必需检查，再与所有 checks 对照；“无 checks”不能等同通过。
若按 head SHA 找不到 run，沿 checks 链接核对；PR workflow 可能使用测试合并提交的 SHA。

## CI 排障流程

1. 对照 checks 链接、run 的 event 与 SHA，确认不是旧提交或无关 push 的结果。
2. 打开失败 job，找第一处有效错误；后续大量错误常由首个失败派生。
3. 记录 workflow、job、matrix、命令、工作目录、Node/包管理器、环境条件。
4. 在本地用同样命令、同样版本、同样依赖复现，先保留失败证据。
5. 判定确定性失败或环境抖动；前者改根因，后者有证据才重跑一次。
6. 修复后先跑最小失败命令，再跑该改动适用的上游门禁。
7. 检查 diff 未引入 lock、生成物或主权文件变化，再推自己的 fork 并核对新 SHA。

```bash
RUN=123456
gh run view "$RUN" -R "$REPO" --json headSha,event,conclusion,jobs
gh run view "$RUN" -R "$REPO" --log-failed
gh run view "$RUN" -R "$REPO" --job JOB_ID --log
```

`--log-failed` 只显示失败步骤；setup、服务启动或上下文不足时看完整 job 日志。
Actions 列表不会包含所有外部 CI；CircleCI 等检查通过 check 链接进入对应日志。
日志无法访问时写明权限限制，请用户或维护者提供脱敏片段；不索要他人凭据。

## 确定性失败还是环境抖动

| 证据 | 判定倾向 | 下一步 |
|---|---|---|
| 相同输入总在同一断言失败 | 确定性 | 本地最小复现并修根因 |
| lint/type 错误指向修改行 | 确定性 | 直接修代码，不重跑赌运气 |
| 同 SHA 有成功也有失败 | 可能抖动 | 比较版本、matrix、日志与服务条件 |
| DNS、下载 5xx、runner 丢失 | 环境抖动候选 | 核对外部状态，符合条件重跑一次 |
| 超时但每次同一慢测试 | 可能确定性性能问题 | 测量耗时，不能只增加 timeout |
| 默认分支也同样失败 | 可能既有问题 | 同版本复现并说明基线，不顺手改 CI |
| 本地通过但远端失败 | 证据不足 | 比较 OS、Node、依赖、时区与服务 |

“同 SHA 一次绿”不是已证明无 bug；竞态与顺序依赖也会间歇出现。
外部网络错误要保留具体状态码与失败阶段；不能只凭“看起来随机”判抖动。

## 本地复现的正确做法

```bash
git rev-parse HEAD
node --version
npm --version
node -p 'JSON.stringify({node:process.version,platform:process.platform,arch:process.arch,TZ:process.env.TZ,locale:Intl.DateTimeFormat().resolvedOptions().locale})'
git status --short
git grep -nE 'node-version|working-directory|npm ci|pnpm |yarn |TZ:|LANG:' -- .github/workflows
```

使用 workflow 固定的 Node 版本与 packageManager，不自行升级到“最新”。
安装命令也照 workflow：`npm ci`、冻结 pnpm/yarn 安装不可互换。
核对 lock 是否与 base 相同，但不修改、不提交 lock；冲突无法消除就报告用户。
复制必要的公开 env 与服务配置；不把 CI secret 下载到本地，不假造权限环境。
先在同 SHA 验证失败；修复后用同命令比较，避免把环境变化误认为代码修复。
仅当上游明确配置这些环境时才按其值设置 `TZ`、`LANG`，不可用改环境藏失败。

## 常见失败速查

| 失败 | 常见根因 | 修法 | 不该由你修 |
|---|---|---|---|
| lint | 未用变量、规则违例、导入顺序 | 跑项目 lint，局部按既有风格修 | 修改规则或全仓格式化 |
| 类型 | 新分支类型未收窄、签名不兼容 | 修必要类型与调用，重跑 typecheck | 用 any/忽略标记掩盖契约 |
| 测试 | 行为回归、fixture 不符、竞态 | 最小复现，补先失败后通过测试 | 删断言、无依据改快照 |
| 构建 | 路径大小写、导出缺失、环境差异 | 同构建命令与工作目录复现 | 改发布/CI 配置、手改产物 |
| lock 不一致 | 声明与锁图不符、安装器版本错 | 核对 base 与包管理器，恢复非必要声明改动 | 任何 lock diff；需同步则停止报告 |
| Node 不匹配 | 本机与 matrix 主版本不同 | 用上游固定版本重跑 | 升级 CI Node、改支持范围 |
| 时区/locale | 隐式本地日期、排序、格式化 | 按契约显式处理并加测试 | 为过测试改全局 CI 环境 |
| 网络依赖 | DNS、限流、下载 5xx、服务不可用 | 确认外部故障，有据重跑一次 | 换私有镜像、嵌入凭据、放宽安全检查 |

测试本来就依赖真实网络时，不擅自重写整套测试架构；先确认本次修复的必要范围。
构建所需外部服务不可得时，明确未验证项；本地无法运行不代表远端一定通过。

## 重跑 CI 的边界

| 正当场景 | 必须附的证据 |
|---|---|
| runner 初始化失败或被平台取消 | 失败阶段在代码执行之前 |
| 下载服务暂时 5xx/DNS 失败 | 具体日志与同类外部故障证据 |
| 维护者明确要求重跑瞬时故障 | 原评审/评论与对应 run |

| 不正当场景 | 应做什么 |
|---|---|
| lint/type/固定断言失败 | 本地修复后推新提交 |
| 没读日志就点重跑 | 先定位失败命令 |
| 一直重跑直到绿 | 停下调查竞态或环境差异 |
| 需要维护者批准 fork workflow | 等批准，不改权限或绕过 |

有正常重跑权限且已授权跟进自己的 PR 时，可以对抖动失败重跑一次。

```bash
gh run rerun "$RUN" -R "$REPO" --failed
```

无权限就报告维护者；不能通过 `--admin`、改 workflow 或拿更高权限凭据解决。
重跑后记录结果；相同故障再现时继续排障，不连续重跑。

## 逐条回应 review

先读完整评论、代码位置与上下文；一个回复对应一个评审点，不把多个意见合成含糊答复。
下列模板中的内容按真实证据填写；尚未完成时不写“已改”。

| 状态 | 回复模板 |
|---|---|
| 认同并已改 | “已改为 <写法>，对应 <提交/文件>；运行 <命令> 通过，覆盖 <场景>。” |
| 不认同并给理由 | “这里保留 <实现> 是因为 <约束>。用 <输入/命令> 对比得到 <结果>；如果需要 <另一行为>，我可以按该契约调整。” |
| 需要澄清 | “我理解为 <具体行为>。边界 <A> 应返回 <X> 还是 <Y>？这会决定 <实现/测试>。” |
| 当前无法验证 | “<检查> 需要 <不可得条件>；已验证 <范围>，尚不能确认 <结论>。” |

给证据时提供最小输入、命令、前后结果与提交位置；基准包含环境和重复次数。
引用规范时贴相关原文位置，不用“行业最佳实践”压过项目约定。
意见不同可以写“这个输入会改变现有行为，证据如下”，避免“你没理解”或反复辩论。
若维护者确认取舍，按其决定调整；涉及硬红线则说明边界并停止相关操作。
不要未经维护者确认就标记对话 resolved；按项目约定由 reviewer 验收。

## 四种典型修改要求

| 要求 | 动作 | 验证与回复 |
|---|---|---|
| 改写法 | 参考相邻代码，局部改命名或控制流 | 证明行为不变并跑相关测试 |
| 拆 PR | 保留最小可独立验证修复，其余移出 | 更新标题正文，说明留下的范围 |
| 换实现 | 先确认约束与边界，再替换实现 | 同一回归测试证明两次行为契约 |
| 补测试 | 加真实缺失边界测试，确认修复前失败 | 给测试名、命令与前后结果 |

拆分时不自动多开一批 PR；其余方向重新过四道门并确认当前授权。
不要为整理历史擅自强推；按上游政策与用户授权处理共享分支。
补改后重新检查完整 diff 与适用门禁，正文更新为最终实现，不保留过时验证声明。

## 长期无响应、被 close 与完成

等待 7～14 天后可一次礼貌跟进：“已按 <意见> 更新，<检查> 通过；若方向仍不合适，请告知。”
之后不再刷评论；记录 PR URL、最后状态与未决项，不给维护者设回复期限。
被 close 时先读理由；若未说明，可一次询问“是方向不符还是实现仍有问题？”
方向不符就记录教训、换候选；不通过改标题、重开重复 PR 绕过关闭决定。
merged 后记录最终链接和结果；closed 后记录原因；未响应则如实标为等待，不能声称已合入。

## 绝对不能做

- 不给自己的 PR approve，不 merge 自己的 PR，不改别人 PR。
- 不使用 `--admin` 绕过门禁或权限，不往 upstream 推；只推自己的 fork。
- 不连续催促，不批量刷 PR，不伪造验证通过或 review 同意。
- 不篡改标题掩盖范围；实现变化后同步更新标题、正文和影响面。
- 不把未脱敏日志、内部地址、用户数据、密钥放入回复或附件。
