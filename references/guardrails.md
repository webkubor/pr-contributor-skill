> 用途：阶段 3 · 价值门禁筛候选、阶段 5 · 写改动及阶段 6 · 开 PR 前检查拒收模式与权限边界。

# 会被拒绝的 PR 模式全集 + 安全边界

通过信号门、范围门、可验证门、相关门，才继续阶段 4 · 搭好分支。
“技术上能改”不代表外部贡献者有权替维护者做决定；用户授权也不能消除上游明确拒绝。
下表中的“改造”是换成合格贡献方向，不是给禁止文件增加例外。

## 低价值与范围失控

| 模式 | 维护者会怎么想 | 合格改造 |
|---|---|---|
| 纯格式化 | blame 被打乱，却没有行为收益 | 放弃；必要格式仅限实际修复行 |
| 纯改名 | 所有调用都要重看，问题是什么 | 放弃；只在真实 bug 的必要范围调整 |
| 纯注释 | 增加要维护的描述，未解决用户问题 | 找到文档错误的外部信号并实际验证 |
| 顺手清理无关代码 | 无法把 diff 对上问题 | 移出本 PR，单独过四道门 |
| 大范围重构 | 风险与审阅成本无法估算 | 缩到局部修复；方向不明先问用户 |
| AI 批量改动未实测 | 每处都要替作者验证 | 只留一个已复现、已验证的修复 |
| 一个 PR 修多个 issue | 回退一个会影响另一个 | 按可独立验证的行为拆 PR |
| 标题小修、实际重写模块 | 范围被隐瞒，无法建立信任 | 如实描述并拆小，不靠改标题掩盖 |
| 无依据的性能优化 | 微基准与用户场景可能无关 | 先给真实场景、基线与可复现测量 |
| 只为得贡献记录改拼写 | 审核成本大于收益 | 只修会误导操作或改变含义的文档问题 |

## 生成物、依赖与外部代码

| 模式 | 维护者会怎么想 | 合格改造 |
|---|---|---|
| 修改 package-lock.json 等 lock 文件 | 安装图被重写，难以核对来源 | 本 skill 一律不改、不提交 lock diff |
| 手改 codegen 产物 | 下次生成覆盖，真源仍然错 | 找到源文件；需产物才能成立则停下问用户 |
| 修改 vendor 目录 | 与上游同步路径冲突 | 去原始依赖项目找信号，当前候选放弃 |
| 无 issue 的依赖升级 | 要替作者承担升级兼容成本 | 有 issue/advisory 才考虑版本声明修复 |
| 更新整个依赖树 | 无法分辨安全修复与附带变化 | 仅处理有据可依的声明；锁文件仍禁止 |
| 为过测试删断言 | 红灯被藏起来，行为没修 | 保留断言，修根因并给先失败后通过证据 |
| 把本机生成缓存提交 | 仓库承受环境噪音 | 移除缓存，仅保留必要源码与测试 |

修 advisory 的版本声明可以成为候选，但任何 lock 文件 diff 都禁止提交。
如果项目流程要求同步 lock 或生成物，当前贡献在本 skill 内不能交付完整结果；停止推送并报告冲突。
不要通过移除 lock diff 后提交一个不可安装的状态来“满足规则”。

## 维护者主权与项目决策

| 模式 | 维护者会怎么想 | 合格改造 |
|---|---|---|
| 改 CI 配置 | 外部作者在改验证规则 | 只读日志，提交证据；不改 workflow |
| 改发布流程 | 可能影响所有下游用户 | 报告复现与建议，由维护者处理 |
| 改权限、token scopes | 扩大信任范围，贡献者无此职责 | 不改，停止该方向 |
| 改 CODEOWNERS | 替维护者决定谁有审核权 | 不改，报告路径归属问题 |
| 改 DCO 检查 | 在降低贡献合规要求 | 按现有要求 sign-off，不动规则 |
| 改 LICENSE | 作者无权替所有权利人授权 | 不改；有疑问交用户与维护者判断 |
| 改 CODE_OF_CONDUCT | 在替社区制定治理政策 | 不改；按已有渠道反馈 |
| 维护者拒绝功能后硬提 | 没尊重已作出的产品决定 | 放弃，除非维护者明确重新开启讨论 |
| 偷改默认行为或公共 API | 下游会遭遇未说明的破坏 | 停下说明影响，先确认方向再重做 |
| 自己 approve / merge | 作者绕过独立审核 | 交给维护者，不执行自批自合 |
| 使用 --admin 绕过门禁 | 以权限代替正确性 | 绝不执行，修复或报告失败 |

“必须先问用户”用于方向不明、超出原范围等决策；不是让用户批准突破硬红线。
上游贡献要求修改主权文件时，说明本 skill 不执行这类变更，交回用户决定后续途径。

## 协作、重复与隐私

| 模式 | 维护者会怎么想 | 合格改造 |
|---|---|---|
| 同一 issue 已有 open PR | 多人竞争同一修复，浪费评审 | 换候选；不要另开重复 PR |
| 改别人 PR | 作者意图和责任被混淆 | 只处理自己的 fork 与 PR |
| 伪造作者或冒充人 | 无法确认责任与授权来源 | 使用真实身份，按上游要求披露 AI |
| 硬编码密钥 | 合入即造成泄漏 | 停止提交，使用无敏感值的配置接口 |
| 内网地址、用户数据进日志 | 公开贡献携带不可撤回的数据 | 用合成输入，脱敏后重新验证 |
| 连续催促、批量刷 PR | 贡献在消耗社区管理时间 | 一个 repo 控制数量，按阶段 7 跟进 |
| 把维护者意见改写成已同意 | 讨论记录与事实不符 | 引原评论，未确认则标待澄清 |

## 安全边界表

| 级别 | 行为 | 判定动作 |
|---|---|---|
| 绝对不做 | 往 upstream 推、--admin、改别人 PR、自批自合 | 即使凭据可用也停止 |
| 绝对不做 | 改 CI、发布、权限、CODEOWNERS、DCO | 只读和报告，不提交 |
| 绝对不做 | 提交 lock、生成物、vendor | 排除候选或停止交付 |
| 绝对不做 | 泄漏密钥、内部地址、用户数据；伪造作者 | 清理内容并报告，不推送 |
| 绝对不做 | 隐瞒范围、绕过上游已明确否决的决定 | 撤出该方向 |
| 必须先问用户 | 值不值得提、方向不确定、证据冲突 | 给候选与代价，等待方向 |
| 必须先问用户 | 公共 API / 默认行为变更、范围明显扩大 | 说明下游影响并暂停依赖动作 |
| 必须先问用户 | CLA 需要本人法律承诺、环境无法验证 | 提供具体阻塞，不能代签或声称通过 |
| 可以直接做 | 读规范、查 issue/PR、fetch upstream | 保留原始证据 |
| 可以直接做 | 已过四道门的局部实现与回归测试 | 同风格、最小改动、项目命令验证 |
| 可以直接做 | 本地 diff 检查、准备标题正文、跟进自己 PR | 始终遵守用户现有授权与硬红线 |

## 越权检测：先看路径，再看语义

在目标仓目录执行，先确定真实默认分支；新增未跟踪文件也要单独检查。

```bash
DEFAULT=$(gh api repos/OWNER/REPO --jq '.default_branch')
BASE="upstream/$DEFAULT"
git diff --name-only "$BASE"...HEAD
git diff --name-only
git diff --cached --name-only
git ls-files --others --exclude-standard
```

对每一份路径列表运行下列筛选；命中就停下核对，不能自动删除文件。

```bash
git diff --name-only "$BASE"...HEAD | grep -Ei \
'(^|/)(vendor|generated|dist|build)/|(^|/)(CODEOWNERS|LICENSE[^/]*|COPYING[^/]*|CODE_OF_CONDUCT[^/]*|DCO[^/]*)$|(^|/)(package-lock\.json|npm-shrinkwrap\.json|yarn\.lock|pnpm-lock\.yaml|Cargo\.lock|poetry\.lock|uv\.lock|Gemfile\.lock|go\.sum)$|^\.github/workflows/|^\.circleci/|(^|/)(release|permissions)(/|\.)'
git diff --stat "$BASE"...HEAD
git diff --check "$BASE"...HEAD
```

`grep` 返回 1 仅表示没命中；路径筛选不是安全证明。
再检查 `.gitattributes` 的 generated 标记、文件头“DO NOT EDIT”、项目 codegen 说明。
权限变更可能藏在普通配置里；阅读完整 diff 中的 auth、scope、role、release 语义。
检查 staged 与未提交 diff，防止只审 HEAD 漏掉待提交的越界文件。

```bash
git diff --cached | grep -nEi \
'(api[_-]?key|secret|token|password|BEGIN [A-Z ]*PRIVATE KEY)[:=]'
```

此扫描只给线索，会误报变量名也会漏报真实密钥；逐段检查日志、截图和 fixture。
发现泄漏后停止 push，通知用户处理撤销/轮换；不要在回复里重贴敏感值。

## 维护者视角的案例式教训

以下是匿名情境，不对应具体项目或真实事件。

| 情境 | 维护者视角 | 应交付的结果 |
|---|---|---|
| 修空输入却格式化全目录 | “我得先从几百行里找出两行逻辑。” | 只留必要分支与一个回归测试 |
| 为修测试放宽 CI 规则 | “测试已经不再证明承诺的行为。” | 同命令复现，修实现；不碰 CI |
| 安全升级夹带 lock 重写 | “依赖树变化远超这条 advisory。” | 停止该候选，解释 lock 冲突 |
| 没有复现就改十处空值处理 | “每一处都可能改变正常输入语义。” | 只修有失败证据的一处 |
| issue 下已有实现仍开新 PR | “两份贡献都要评审，还得协调作者。” | 选择尚未有人处理的信号 |
| 标题说文档修复却改 API | “第一屏无法告诉我升级风险。” | 如实说明影响，先确认方向 |

交付前复查：一个外部理由、一件事、项目自己的验证、无越界路径、无隐瞒影响。
任一项无法回答，就回到阶段 3 · 价值门禁；不要把不确定性转嫁给维护者。
